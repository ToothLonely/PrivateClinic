# Правила работы в проекте

## План и Git Task

- Работай по [русскому гайду Git Task](https://github.com/ToothLonely/TaskPlugin#russian). Для редких операций сверяйся с [полной документацией](https://github.com/ToothLonely/TaskPlugin/blob/master/DOCUMENTATION.md#russian).
- При составлении плана используй формат Git Task: `.git-task/plan.json`, целевая ветка в `target_branch`, задачи в массиве `tasks` в порядке исполнения. У каждой задачи заполняй `title` и `description`. Заголовок называет результат. Описание служит самостоятельным промптом для агента без доступа к переписке: сценарий, границы, затронутые платформы, критерии приёмки, режим работы и первая роль. В каждом description дай отдельные промпты исполнителю и проверяющему. Служебные поля и историю ведёт плагин. Веди единый пополняемый план проекта в `.git-task/plan.json`. Добавляй следующие этапы в этот план, сохраняя ID, попытки и историю существующих задач.
- После настройки инфраструктуры планируй работу по пользовательским функциям. Одна задача доводит сценарий до готовности, включая нужные ему изменения клиента, сервера, хранения и проверок. Требования к конкретной функции записывай в задачу.
- При подключении проекта следуй требованиям гайда к версии Git, автору коммитов и целевой ветке с начальным коммитом. Для нового плана используй `git task init`, после заполнения — `git task init --apply`, `git task hooks install` и `git task status`.
- В начале сессии проверь `git status`, текущую ветку и `git task status`. Первая роль начинает выбранную задачу из чистого рабочего дерева командой `git task start <ветка> --id <id>`. Обе роли работают **последовательно в одной ветке одной задачи**. При передаче следующая роль сверяет ID, ветку и коммит и продолжает текущую попытку. Сохраняй пользовательские изменения.

## Роли и порядок работы

Выбирай режим при составлении задачи. **TDD** подходит, когда ожидаемый результат можно заранее выразить воспроизводимым тестом: правило фильтрации, переход состояния, вытеснение из кэша, разрешение конфликта или воспроизведение ошибки. **Обычный режим** подходит для настройки сборки, подключения инфраструктуры, вёрстки и задач, результат которых лучше проверить на работающей интеграции. Если функция сочетает оба случая, укажи в описании, какое поведение покрывается TDD и как проверяется остальная часть.

### TDD: проверяющий → исполнитель → проверяющий

1. Проверяющий читает критерии, пишет тест на ближайшее наблюдаемое поведение и запускает его. Убедившись, что причина падения связана с отсутствующим поведением, передаёт тест, команду и результат исполнителю. Поломка среды не подтверждает стадию Red.
2. Исполнитель реализует поведение, запускает полученные тесты, затем при необходимости упрощает код и запускает тесты снова. Дублировать тест проверяющего не требуется. Если ожидание теста противоречит задаче, вынеси расхождение на обсуждение. Не ослабляй проверку ради зелёного результата.
3. Проверяющий сверяет реализацию с критериями, сам запускает нужные проверки на полученном коммите и проверяет пограничные случаи. При необходимости роли повторяют цикл для следующего правила или исправления.

### Обычный режим: исполнитель → проверяющий

1. Исполнитель реализует задачу, добавляет быстрые тесты для затронутой логики и запускает их. Для настройки или визуальной правки использует подходящую сборку, запуск или проверку интерфейса.
2. Проверяющий независимо проверяет ожидаемый результат. Добавляет интеграционный, платформенный или сквозной тест, когда тот ловит конкретную ошибку, которую пропустят быстрые проверки. Подбирает набор запусков по изменению.

При передаче между сессиями укажи задачу, ветку, коммит, команды, результаты и оставшуюся работу. Зафиксируй передаваемые изменения в ветке задачи. Проверяющий возвращает воспроизводимое замечание исполнителю и перепроверяет исправление. После принятия результата и включения коммитов в целевую ветку сверь статус через Git Task. Для squash и cherry-pick применяй предусмотренный гайдом порядок завершения.

## Реализация утверждённого интерфейса

- Для каждой задачи, затрагивающей UI, исполнитель и проверяющий читают [спецификацию «Синий акцент»](output/design/blue-accent/DESIGN.md) и открывают соответствующее состояние [утверждённого макета](output/design/blue-accent/index.html). Это относится также к каркасу и временно пустым экранам. В description укажи конкретные экраны и состояния для обеих ролей.
- Переноси заданные цвета по назначению, иконки, расположение, размеры, начертания и поведение. Точные координаты на нужной ширине получай из прототипа через [измеритель](output/design/blue-accent/measure.cjs). Значения по умолчанию из UI-библиотеки допустимы при совпадении с эталоном.
- Если ни задача, ни утверждённый макет не определяют вид элемента или его состояние, либо они противоречат друг другу, задай владельцу конкретный вопрос **до реализации этой части**. Сохраняй эталон до нового решения владельца.
- Исполнитель и проверяющий отдельно сверяют снимки настоящей сборки с эталоном на затронутых ширинах в обеих темах. В передаче указывают измерения, пути к снимкам, выявленные расхождения и непроверенные платформы. Расхождение остаётся в текущей задаче до исправления или явного решения владельца.

## Структура Compose UI

- В каждом Kotlin-файле с Compose UI размещай ровно одну основную `@Composable`-функцию и ровно одну её `@Preview`-функцию. Имя файла совпадает с именем основной функции. Другие функции выноси в отдельные файлы. Каждый вложенный или приватный компонент, которому нужна собственная `@Composable`-функция, получает отдельный файл со своим превью.
- Группируй файлы по папкам и пакетам соответствующих экранов и функций приложения. Компоненты, которые используют разные экраны, размещай в отдельных папках общих компонентов по их назначению. Превью размещай рядом с компонентом и задавай для него локальные примеры состояния.

## Архитектура и качество

- Развивай Android, iOS, веб и бэкенд в многомодульном монорепозитории. Выделяй модули по ответственности. Для клиентов используй Kotlin Multiplatform, Compose Multiplatform, MVVM и однонаправленный поток данных. Общую логику держи в общих source sets, системные API — в платформенных реализациях.
- Перед содержательным изменением изучи затронутый код, тесты и относящийся к задаче пример. Для структуры и общего UI используй [документацию KMP](https://kotlinlang.org/docs/multiplatform/multiplatform-discover-project.html) и [KotlinConf App](https://github.com/JetBrains/kotlinconf-app). Для состояния экранов, репозиториев и тестов используй [Now in Android](https://github.com/android/nowinandroid) и [руководство по offline-first](https://developer.android.com/topic/architecture/data-layer/offline-first). Для iOS сверяйся с [Apple Developer](https://developer.apple.com/documentation/) и [HIG](https://developer.apple.com/design/human-interface-guidelines/), для браузерного поведения — с [MDN](https://developer.mozilla.org/). При переносе решения проверь его применимость к целевым платформам.
- В юнит-тестах проверяй наблюдаемое поведение, используй простые fake-реализации зависимостей. Постоянное хранение, сетевые контракты и платформенные интеграции проверяй на соответствующей границе. Сохраняй полезные тесты проверяющего рядом с тестами проекта.
- При подборе зависимостей проверяй совместимость целей и фиксируй версии. Решения, меняющие согласованный пользовательский сценарий, согласуй с владельцем проекта.
- В отчёте перечисли реализованные критерии, фактически выполненные проверки и оставшиеся ограничения. Сборку и запуск iOS проверяй на macOS. Если Mac недоступен, явно укажи, какая проверка ждёт запуска.
